# 러스트 전환 기초 구상

자본주의 시뮬레이터를 러스트로 옮기기 위한 첫 설계예요. 지금 코드를 실제로 세어 보고 정했어요.

## 1. 결론부터

- **화면은 러스트(Leptos)로 만들어 WASM으로 돌려요.** 사이트는 지금처럼 GitHub Pages에 올리는 정적 사이트로 남아요. 아이폰 홈 화면 추가, 도메인, 나중의 APK 계획은 그대로 가요.
- **파이어베이스 연결은 지금의 JS 파일(`app/firebase.src.js`)을 다리로 남겨요.** 러스트는 이 다리를 타입이 있는 함수로 감싸서 불러요. 이유는 3.2에 있어요.
- **한 번에 다 바꾸지 않고, 화면 하나씩 바꿔요.** 바꾼 화면도 같은 id와 class를 쓰게 해서, 지금 있는 화면 시험으로 그대로 확인해요.
- **CSS(`app/app.css`, `app/tokens.css`)는 바꾸지 않아요.** 러스트가 같은 class 이름으로 화면을 그리면 모양이 그대로예요.

## 3. 큰 결정과 이유

### 3.1 화면 기술: Leptos (브라우저에서만 그리는 방식)

- **추천: Leptos.** 바뀐 부분만 다시 그리는 방식이라서, 지금처럼 화면을 통째로 다시 쓰는 코드보다 깜빡임이 적어요. 웹 화면을 만드는 러스트 도구 중 가장 많이 쓰여요.
- 다른 후보:
  - **Dioxus**: 리액트와 비슷하게 쓰고, 안드로이드 앱도 같은 코드로 만들 수 있어요. 나중에 네이티브 기능이 꼭 필요하면 다시 볼 만해요.
  - **Yew**: 오래됐지만 Leptos보다 느리고 덜 쓰여요.
- 시작할 때 그 시점의 Leptos 최신 안정판을 확인하고 버전을 고정해요.

### 3.2 파이어베이스: JS 다리를 남겨요

러스트용 공식 파이어베이스 SDK는 없어요. 선택지는 두 가지예요.

| 방법 | 장점 | 문제 |
| --- | --- | --- |
| **A. JS 다리 유지 (추천)** | 실시간 듣기(대화 목록, 메시지, 지갑), 트랜잭션, 로그인 유지가 지금처럼 그대로 돼요. 보안 규칙과 시험도 그대로예요. | 러스트와 JS 사이에 얇은 연결 코드가 필요해요. |
| B. 러스트에서 REST 직접 호출 | JS가 사라져요. | Firestore 실시간 듣기는 브라우저에서 REST로 할 수 없어요. 계속 다시 읽어야 해서, CLAUDE.md의 "서버를 아끼는 구조(최근 40개만 듣기)"를 지킬 수 없어요. 로그인 토큰 갱신도 직접 만들어야 해요. |

지금 다리가 쓰는 기능은 실시간 듣기 3곳, 트랜잭션 8곳, 묶음 쓰기 11곳, 개수 세기 2곳, 서버 시각 26곳이에요. 이걸 러스트로 다시 만들면 위험이 크고 얻는 게 적어요. 그래서 **A로 가요.** 나중에 실시간이 필요 없는 부분(목록 읽기 등)만 B로 옮길지 다시 판단해요.

러스트 쪽에서는 `window.cloud`의 함수 78개를 타입이 있는 함수로 감싸요. 예를 들어 `shopBuy(cid, pid, n)`은 러스트에서 `cloud::shop_buy(&cid, &pid, n).await -> Result<u32, CloudError>`처럼 보여요. 데이터 모양(상품, 연구실, 상태, 공지, 대화, 메시지, 지갑, 회사, 인벤토리)은 serde 구조체로 정해요.

### 3.3 그대로 둘 JS

- `app/tabbar.js` (WebGL 유리 탭 바): 혼자 돌아가는 부품이고, 러스트로 옮겨도 얻는 게 없어요. 러스트는 탭이 바뀌었다는 신호만 주고받아요. 마지막에 꼭 필요하면 다시 봐요.
- `app/backdrop.js` + `vendor/html2canvas`: 화면을 사진으로 찍는 부분이에요. html2canvas는 화면(DOM)을 읽기만 해서, 화면을 러스트가 그려도 그대로 동작해요.
- `app/guard.js`: 다른 사이트의 액자 안에서 열리는 것을 막는 10줄짜리 파일이에요. 페이지 맨 처음에 돌아야 해서 JS로 둬요.

### 3.4 APK

APK는 러스트 전환과 상관없이 만들 수 있어요. 지금 웹앱을 그대로 감싸는 방식(TWA, Bubblewrap)이 가장 간단하고, 도메인에 `/.well-known/assetlinks.json`만 추가하면 돼요. 러스트로 바꾼 뒤에도 같은 방법을 써요.

## 4. 옮기는 방법: 한 화면씩

### 원칙

1. **같은 이름 유지**: 바꾼 화면도 같은 `id`, 같은 `class`, 같은 `window.Shop` 같은 이름을 써요. 그러면 `tests/e2e`의 화면 시험이 고치지 않고 그대로 돌아가요.
2. **한 번에 한 화면**: 한 화면을 바꾸고, 시험을 통과하면 올리고, 다음 화면으로 가요. 중간에 멈춰도 사이트는 항상 동작해요.
3. **사용자 글은 문자로만**: 지금은 `esc()`를 거쳐 `innerHTML`로 넣는데, 러스트에서는 Leptos가 글자를 자동으로 문자 처리해요. 사진은 지금의 `safeImg()`와 같은 검사 함수를 러스트에 만들어 써요.

### 순서

| 단계 | 화면 | 파일 (줄 수) | 이 순서인 이유 |
| --- | --- | --- | --- |
| 1 | 공지 | `notice.js` (137) | 작고 혼자 돌아가요. 다리, 빌드, 배포를 시험하기 좋아요. |
| 2 | 인벤토리 | `inv.js` (152) | 먹기(트랜잭션)를 처음 다뤄요. |
| 3 | 관리 | `manage.js` (147) | 자동 검색, 인증토큰 흐름을 옮겨요. |
| 4 | 상점 | `shop.js` (207) + `shapes.js` (396) | 상품 그림을 여기서 같이 옮겨요. |
| 5 | 일 탭 | `work.js` (912) | 공장, 일하기, 성능 화면이에요. |
| 6 | 사업 탭 | `biz.js` (1,315) | 시장, 연구실, 꾹 눌러 옮기기가 있어요. |

## 5. 러스트 폴더 구조 (제안)

```
web/
  Cargo.toml            # 작업 공간
  crates/
    cloud/              # window.cloud 감싸기, 데이터 구조체, 오류 종류
    ui/                 # 화면 부품: notice, inventory, manage, shop, work, biz, money, messages ...
    app/                # 시작점: 화면마다 정해진 자리(#notices-root 등)에 붙여요
app/rs/                 # 빌드 결과 (wasm, 연결 JS). index.html이 불러요
```

처음에는 `wasm-pack build --target web`으로 만든 결과를 지금의 `index.html`이 불러요. 모든 화면이 러스트로 바뀐 뒤에 Trunk 같은 전용 빌드 도구로 바꿀지 다시 정해요.

## 6. 바뀌는 설정

- **CSP**: WASM을 돌리려면 `index.html`의 `script-src`에 `'wasm-unsafe-eval'`을 넣어야 해요. 그 밖의 막는 규칙은 그대로예요.
- **배포**: 지금은 브랜치를 그대로 올려요. 러스트를 쓰면 빌드가 필요해서, GitHub Actions에서 WASM과 `app/firebase.js`를 만든 뒤 Pages에 올리는 방식으로 바꿔요. `CNAME`(도메인)은 결과물에 꼭 같이 넣어요.
- **캐시 버전**: 지금처럼 `?v=` 숫자를 손으로 올리는 대신, 빌드할 때 파일 이름에 내용 기반 해시를 붙여요.
- **크기**: WASM은 처음 받을 때 무거울 수 있어요. 크기 최적화(`opt-level = "z"`, LTO, `wasm-opt`)를 켜고, 단계마다 크기를 재서 기록해요.

## 7. 확인 방법

- **보안 규칙 시험** (`cd tests && npm run rules`, 107개): 서버 규칙은 바뀌지 않으니 그대로 통과해야 해요.
- **화면 시험** (`tests/e2e`, 12개): 화면 하나를 바꿀 때마다 돌려요.
  ```
  cd tests && npm run build && EMU=1 node build.mjs && sh e2e/run.sh
  ```
  특정 시험만 돌리려면 `sh e2e/run.sh notice cats`처럼 이름을 붙여요.
- **러스트 시험**: 다리 감싸기와 계산(공장 정산, 먹기 양, 닳는 값)은 `wasm-bindgen-test`로 브라우저 안에서 시험해요.
- **아이폰 확인**: 단계마다 홈 화면 앱에서 한 번씩 열어 봐요. 특히 1단계 뒤에는 WASM이 아이폰에서 잘 뜨는지 꼭 봐요.

## 8. 위험과 대비

| 위험 | 대비 |
| --- | --- |
| WASM 첫 로딩이 느려요 | 크기 최적화, 단계마다 크기 기록. 로그인 전 화면은 가볍게 유지해요. |
| JS와 러스트 사이의 값 변환 실수 | 다리 함수마다 구조체를 정하고, 변환 실패를 오류로 드러내요. |
| Leptos 버전이 자주 바뀌어요 | 버전을 고정하고, 올릴 때는 한 번에 한 단계씩 올려요. |
| 두 언어가 섞이는 기간이 길어요 | 화면 단위로 끝내고, 반쯤 옮긴 화면을 남기지 않아요. |
| 시험이 없는 부분 (돈 탭, 대화방 일부) | 그 단계 전에 화면 시험을 먼저 추가해요. |

## 9. 솔직한 기대치

- **좋아지는 것**: 타입 검사로 실수가 줄어요. 화면 상태 관리가 정리돼서, 이번에 겪은 깜빡임이나 중복 id 같은 버그가 생기기 어려워요.
- **그대로인 것**: 파이어베이스는 JS로 남고, 보안은 지금처럼 서버 규칙이 지켜요. 앱이 눈에 띄게 빨라지지는 않아요. 지금 느린 부분은 대부분 서버 읽기와 그림(WebGL, 사진 찍기)이라서 언어와 관계가 적어요.
- **비용**: 약 5,800줄을 다시 쓰고, 빌드와 배포 과정이 생겨요.

## 11. 다음에 바로 할 일 (1단계)

1. `web/` 작업 공간과 세 크레이트(`cloud`, `ui`, `app`)를 만들어요.
2. CSP에 `'wasm-unsafe-eval'`을 넣고, GitHub Actions 빌드·배포를 만들어요.
3. `cloud` 크레이트에 공지 관련 다리 함수 5개(`noticeIds`, `noticeList`, `unseenNotice`, `markNoticeSeen`, `voteNotice`)를 감싸요.
4. 공지 화면(`#notices-root`와 한 번 뜨는 전체 화면 공지)을 Leptos로 다시 만들고 `window.Notices`를 러스트가 맡아요.
5. `sh e2e/run.sh notice`와 규칙 시험을 통과시키고, 아이폰 홈 화면 앱에서 열어 봐요.
